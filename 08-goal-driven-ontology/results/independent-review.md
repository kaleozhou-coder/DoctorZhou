## 首轮发现及修订后状态

以下是首轮发现。**代码作者随后修复第1–3项；复核者已重新读取代码并独立运行，10个单测通过，28条夹具与10个变异结果保持。** 补丁后脚本 SHA256：`b363ff9b467f2aaf1911f7c96ab60b07de8a1dcea2ed0816e2a128bf5af15435`。第4项仍须在冻结主实验前补清。

1. **已修复：撤销未知状态被默认为有效。** 对 C01 的唯一记录设置 `revoked=None`，甚至删除该字段，当前仍返回 `close_eligible`。`record.get('revoked', False)` 只把真值视为撤销，没有区分已核实未撤销与状态未知。应在 P0 契约中明确该字段必须是已验证布尔值并校验，或将未知送审；补缺失/null/非法类型测试。不要宣称已完整验证未知与冲突的安全处理。
2. **已修复所测类型与有限性探针：数量输入校验。** 将 C01 验收数量设成 Python `float('nan')` 返回 `close_eligible`，因为 `<=0` 与 `< invoice_quantity` 均为假。标准 JSON 不允许 NaN，但 Python 默认 JSON 解码可接受它，`decide` 也直接接受字典；Infinity、布尔值和错误类型同样缺乏统一边界。要求有限正数、排除 bool，拒绝非标准数值，并为损坏输入提供稳定的拒答/送审行为；如果只支持可信内部夹具，应明确而非暗示可处理原始业务输入。
3. **实现已修订：已撤销记录的优先级。** C01 加入 `id=E2, revoked=True, policy_version=P_OLD` 的副记录后，返回 `needs_review/unresolved_policy_version`，因为版本和ID检查早于撤销过滤。C28描述“撤销附加记录被忽略”，但仅测试版本及ID正常的撤销记录。需明确：撤销记录是否仍能因旧版本/重复ID阻断？按明确政策补交叉缺陷测试，或收窄 C28 描述。不能未经政策决定直接移动判断顺序。
4. **尚待修订：主终点需预定义未达标的处理。** 研究协议以“达到质量门槛所需真实审阅分钟数”为主终点，但尚未规定预算耗尽仍未达标的任务如何计入。冻结实验前应定义失败/删失处理及共同达标率，不能只比较成功任务用时，否则更常失败的方法可能显得更快。1个百分点风险非劣界和20%节时均仍是待确认阈值，应保持其草案地位。

## 剩余限制与后续验证

- 28条夹具与实现共同设计，存在循环验证；它们证明当前演示器按这些例子执行，不证明业务正确性、泛化或AI生成质量。10项开关消融只展示人工设定规则在特定例子上的作用，不隔离目标驱动方法的因果收益。
- 输入已被人工/AI结构化为订单行、状态、授权布尔值等。没有运行原始单据抽取、来源语义支持检查、独立授权验证、候选生成/审批流程、真正OWL/RDF推理或政策增量更新。类/属性列表不是已执行的本体推理。
- `source_id/source_locator` 仅检查非空，任意伪指针都可通过；代码特征名 `provenance` 不应在报告里简称“来源忠实性已验证”。单位同一性和订单行唯一性也依赖已给定字段，不是从原件核验。
- 不同ID但同一批货或同一来源可重复计数。两个各5件且来源相同、仅ID不同的记录即可关闭10件发票。参考模型已经披露“不重叠批次”假设，因此不列为未披露实现错误，但真实用途必须验证批次/分配量；跨发票重复消费相同验收量也尚未建模。
- 缺少多缺陷组合、别名/近重复、缺失键、非法输入、替代链、政策生效时点等系统性测试。现有顺序不变性测试只反转现有记录集，不构成一般性质证明。
- 拒答/送审不能只当“安全成功”。主实验应同时报告错误关闭、可关闭召回、需证据/需审阅混淆、达到质量门槛比例和完整成本；独立材料家族与真人评审数据仍未取得。
- 应持续在结果摘要旁保留“工程自检”限定；不得将 `accuracy=1.000` 单独展示为业务准确率，或把0/22称为零风险。

结论：**可作为诚实标注的工程演示与研究启动材料；不能作为主方法有效性或上线安全性的证据。** 首轮输入及撤销问题已完成所列探针修复；主终点失败处理仍应进入下一轮协议修订。
