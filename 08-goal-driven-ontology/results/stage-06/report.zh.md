# 课题 8 第六阶段：修复执行边界，并量化保守送审的代价

日期：2026-11-11。性质：合成工程研究。真实模型 A/B 运行、付费调用均为 **0**。

## 摘要

本阶段修复了两个可实证复现的执行边界问题，同时发现：扩大文本拦截范围虽然
堵住已知漏检，却会完全失去旧数据中的正例关闭能力。因此，“不误关”不能单独
代表建模能力或业务价值。

- **枚举 null 绕过已修复**：旧 IR v2 仍能复现非法默认关闭；新 IR v3 在执行前返回
  `needs_review / invalid_artifact`。旧实现、原始失败结果保留不变。
- **又发现并修复一个问题**：`[null,1,1]` 原来用 UNKNOWN 掩盖重复集合成员，导致某些
  合法布尔表达式仍关闭。现在先检查已知成员重复，再传播未知。
- **E22 文本通道漏检变为送审**：入口 v2 对所有已声明自由文本字段统一保守处理，
  但旧 20 个正例的关闭召回从 v1 的 17/20 降为 **0/20**，旧挑战正常控制从 9/10 降为
  **0/10**。这些代价没有通过删文本或改标签掩盖。
- **新 20 条合成探针**：6/6 无文本正常控制保留关闭，5/5 矛盾文本不关闭，7/7 良性
  文本也送审，2/2 政策短缺控制保持原判断与理由。它并没有理解文本的一致或矛盾。
- 全套 **338 项工程测试通过**；49 个第六阶段 JSON 复跑字节一致；第五阶段25个
  结果 JSON 也完整复现。以上都不是338个独立业务样本或真实模型效果。

## 2. 两个执行缺陷的前后证据

### 2.1 枚举提前返回

旧 `_validate` 遇到枚举 `[null]` 返回 UNKNOWN，调用者未验证结果就继续执行，
从而跳过规则列表、出处和默认分支约束。新版本要求枚举为完整有类型值，null、
嵌套缺失和不完整记录直接报错；evaluate 必须看到明确的 `valid is True` 才执行。
集合枚举按类型归一化并拒绝归一化重复值，集合顺序不改变成员判断。

原始失败的[本轮复现](before-adversarial-artifact.json)与
[第五阶段失败](../stage-05/adversarial-artifact.json)均保留；新旧对照见
[独立对抗复测](reviewer-probe-after.json)中的 `legacy_exploit` 与 `fixed_exploit`。

### 2.2 复核发现 UNKNOWN 掩盖重复集合

初版修复虽通过93项 IR 测试，独立复核却发现：合法表达式
`any(true, count(s)==1)` 在 `s=[1,1]` 时拒绝，在 `s=[null,1,1]` 时关闭。
问题不在 true OR UNKNOWN 的逻辑本身，而在非法重复集合被提前降成 UNKNOWN。

修复后，null在三个位置的重复集合均返回 `malformed_input`；唯一已知成员加null
仍按原有三值逻辑处理。新增负向回归后，IR专项为94项。

保留[首次复核原始输出](reviewer-probe.json)、[首次脚本](reviewer-probe.py)、
[修复前源码快照](pre-review-rule_ir_v3.py)、[修复后脚本](reviewer-probe-after.py)与
[详细审阅记录](code-review.md)。源码快照由修复前后差异恢复并核对到首次输出记录的
相同 SHA256，不是事后伪造测试成绩。旧脚本在修复后因原本预期的错误关闭不再出现而
失败，该实际日志也保留在 `reviewer-probe-after-test.log`。

独立复测包括27个畸形产物变异、7个运行时输入及7个入口探针。未发现更多具体绕过
不等于安全证明。有效的“总为真就关闭”规则仍可能违反业务政策；类型校验、来源定位
存在和数据式AST均不证明政策正确、来源可信或生产可用。

## 3. 入口修复的收益与高昂代价

[入口 v2 规范](../../protocol/input-contract-v2.md)复用v1结构校验，把 question、
envelope/source raw_text、source.text、F06段落text全部视为未经核验自由文本。
如果原政策结果会关闭且其中任一字段非空，则送审；原有非关闭结果及理由保留。
没有关键词、样本ID特判或“verified=true”放行开关。

| 旧数据指标 | 基线 | 基线+入口v1 | 基线+入口v2 |
|---|---:|---:|---:|
| 60条状态/主理由正确 | 60/60 | 57/60 | 40/60 |
| 20条正例关闭召回 | 20/20 | 17/20 | 0/20 |
| 40条负例错误关闭 | 0/40 | 0/40 | 0/40 |
| 旧压力22条政策内精确判断 | 22/22 | 22/22 | 14/22 |
| 旧压力8条范围外不关闭 | 4/8 | 8/8 | 8/8 |
| 旧挑战10条正常关闭控制 | 10/10 | 9/10 | 0/10 |
| 旧挑战9条不安全输入不关闭 | 2/9 | 8/9 | 9/9 |
| 旧挑战5条良性扩展送审 | 0/5 | 4/5 | 5/5 |

E22从关闭改为 `needs_review / contract_text_unverified`。但旧输入全部带question
和source.text，很多text只是结构化字段的JSON回声；新契约仍一律保守送审。
这证明它修复了声明通道的处理不一致，**不证明它更懂证据、更有业务价值或更准确**。
来源ID、类别字符串仍是非语义标识，不保证能识别藏在任意字符串中的业务事实。
没有文本的结构化事实也可能为假，契约不证明其真实性。

## 4. 新冻结文本通道探针

作者只读政策和输入结构契约，知道问题类别；未读候选实现、旧案例或标签。
20条在候选执行前冻结。6组三联输入分别覆盖顶层raw_text、source raw_text、
source.text、F06段落text、无关来源text及多通道文本，另有2条政策短缺控制。
question没有纳入这个独立包，其检查只由工程测试覆盖。

| 独立报告的组别 | 基线 | 入口v1 | 入口v2 |
|---|---:|---:|---:|
| 正常无文本控制保留关闭 | 6/6 | 6/6 | 6/6 |
| 矛盾文本不关闭 | 0/5 | 4/5 | 5/5 |
| 良性文本送审成本 | 0/7 | 4/7 | 7/7 |
| 政策短缺判断与理由正确 | 2/2 | 2/2 | 2/2 |

入口v1在新 `PC-T03-CONTRADICTORY` 再次因source.text而漏检；v2拦截，但配对支持性
文本也被拦截。三联组不是独立样本，四个分母不合并为“准确率”。预期按提出的统一
文本边界制定，不能倒过来称v1违反了它从未承诺的source.text语义保证。
原始逐案结果见 [入口v2新探针报告](first-run/gate_v2.prose.report.json)。

评价范围还需说明：作者包带有input_contract_status等完整预期元数据，当前运行器
只把状态/理由用于政策控制，安全组只统计是否不关闭，良性组只统计送审成本；
没有对所有原始预期元数据逐字段评分。契约状态和路径正确性本轮仅由工程测试
覆盖，不能把上述5/5写成完整预期元数据全部验证通过。

## 5. 共同解释器回归及覆盖限制

不加入口时，IR v2/v3在已支持的F01/F05范围输出完全相同：旧20条状态及理由20/20，
6条正例全部关闭，14条负例无错误关闭。旧压力执行11/30，政策内7/7，范围外3/4；
旧挑战执行8/24，正常控制4/4、不安全输入1/2。S27和E06的订单行矛盾仍需入口处理。

入口v2叠加IR v3后，旧20条中14条非关闭判断保留，6个正例全部送审。**它没有扩展
可表达政策范围。** 旧基准40条、旧压力19条、旧挑战16条仍不支持。新20条探针属于
F02/F03/F06，IR配置全部未执行，不能引用基线入口的5/5为IR新增独立覆盖。
