# 课题 8：公开素材核验与实验边界

核验日期：2026-11-06 UTC。已选用官方固定发布路径、小量规范 XML 示例；不是企业真实采购档案，也不是现成完整的应付审核金标准。详细 URL、许可、版本和文件摘要见 data/public/LICENSE-SOURCES.md 与 manifest.json。

## 推荐首轮素材

1. OpenPeppol BIS Billing 3.0 / 2025-Q2：base-example、sales-order-example、base-creditnote-correction。可测试发票编号、主体、行金额、数量、币种、订单引用、付款条款以及更正引用的识别。仅凭这些不能判定应付款可放行。
2. OASIS UBL 2.1 发布目录内的 2.0 Order、Invoice、DespatchAdvice、ReceiptAdvice 示例。可测试跨单据引用、数量和收货差异的候选关系。必须先比较实际单号/行号/单位，不得因同在规范目录就强行组成一个企业交易链。
3. Peppol Logistics Receipt Advice 的九种用例适合定义反例类型，但其示例再分发许可尚不明确，当前只保留官方链接和本研究原创分析。

## 关键业务问答与不可推断项

- “发票引用了什么订单/收货凭证？”必须返回具体 XPath、原文和源文件哈希；引用存在不代表外部文件在手。
- “是否有收货数量与短缺记录？”OASIS ReceiptAdvice 示例明确含 ReceivedQuantity=90 KGM、ShortQuantity=10 KGM，适合测试不可把收到部分货物误判为全部验收。
- “是否已收到发运通知？”须区分收到电子文档与实物收货。Peppol Logistics type D 的 AP 是文档验证语义，不能提升为货物质量验收。
- “是否具备最终验收依据？”规范实例不能提供本企业的验收规则、签署权限、合同验收门槛、完整附件或真实性。默认回答“依据不足/待人工确认”，不能回答“验收不合格”或“验收已通过”。
- “可以付款吗？”需要采购合同、匹配结果、收货/质量验收、争议/退货、审批权限及企业付款制度。Invoice 或 ReceiptAdvice 单独都不充分。

## 分批对照设计建议

建立人工编写、显式标注的研究任务与审核政策，不伪装成现实企业政策。阶段 A 只给发票，阶段 B 给订单与发运，阶段 C 给收货及短缺证据，阶段 D 给研究用验收规则/待补证清单。每个模型候选必须有来源文件、XPath/文本范围、抽取时间、证据类型、支持/缺失/冲突/不适用状态、人审状态。

对照组一次获得完全相同的材料与目标，不得偷偷少给业务问题或人工时间。以同一素材总集、相同模型/预算/人审预算比较目标驱动分批与一次性全量；另设无目标消融时应单独标识，不把两个因素混为一谈。重点评价错误“已验收/可付款”率、来源可定位率、问题覆盖率、补证需求正确率、人工修改量和成本，而不是实体/关系数量。

真实业务最终验收事实不足，是此公开素材的已知限制，不是实验中应由模型补全的空白。若用合成验收记录补齐，应放在 data/synthetic，注明生成者、规则和与原始文件的关联假设。

## 许可与版本提醒

Billing 示例有官方可自由使用说明。OASIS 使用其规范声明许可并保留完整 Notices，不应称为 MIT/CC。Logistics BIS 明确有再分发限制，目前不保存其规范全文或示例包。未使用 EU eProcurement ontology：首轮狭义应付/验收证据任务已足够，避免将招投标术语扩张进来。无 Git commit 可用时以官方发布路径、检索日期和 SHA256 固定；不声称网站版本不可变。

## 实际字节检查结果

7 个 XML 均可由 Python ElementTree 解析，SHA256SUMS 全部通过。OASIS 四文件实际 ID/引用相符：Order=AEG012345；Invoice=A00095678 引用该订单；DespatchAdvice=565899 引用该订单；ReceiptAdvice=658398 引用该订单与该发运单。这支持“规范级关联样例链”，仍不证明跨单金额/行标识/数量完全匹配或企业支付资格。Billing 示例多个文件均用 Snippet1，不应把其 ID 重复当真实重复发票风控结果。sales-order-example 的 OrderReference/ID 是 NA，不能当作已定位真实采购订单。
